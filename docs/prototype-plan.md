# 3D Prototype Plan

Goal: get the overhead "what the car sees" view running in a phone browser, then layer the design
in `docs/game-design.md` on top in small PRs. Each step below is one PR that ends playable on
GitHub Pages, so the owner can try it on their phone after every merge.

Builds on the setup PR (TypeScript + Vite + Vitest, CI, Pages deploy, `npm run screenshot`).

## Tech choices

- **Three.js** for rendering. Plain Three.js, no React/game engine: it fits the no-framework
  setup, is about 150 KB gzipped, and works in mobile Safari and Chrome. Import only what we use so
  Vite can tree-shake.
- **Low-poly, flat-shaded, mostly procedural.** No large models or textures to download. The
  self-driving-screen look is naturally minimal: dark ground, grey boxy cars, glowing lane lines,
  a soft sensor range ring. This keeps it fast on phones and easy to build from code.
- **Camera**: perspective camera behind and above the SUV, tilted down about 55-65°, like a Tesla
  or Waymo screen. The SUV stays fixed near the bottom third of the screen and the world scrolls.
- **Logic stays pure.** `game.ts` (and new modules like `route.ts`, `autonomy.ts`, `economy.ts`)
  stay DOM-free and unit tested. The renderer reads state; it never owns game rules.
- **Phone performance budget**: cap device pixel ratio at 2, fewer than ~100 draw calls (use
  `InstancedMesh` for trees, posts, traffic), no real-time shadows at first, pause rendering when
  the tab is hidden. Target 60 fps on a mid-range phone, graceful at 30.
- **Verification from the cloud**: `npm run screenshot` already drives headless Chromium. WebGL
  works there through SwiftShader (software rendering), so screenshots of the 3D view are possible.
  We add a `?seed=` / `?state=` URL option so a screenshot can show a fixed scene.

## Real-world map on a static site

**Decided (owner):** the game uses real road data on a real map, with real buildings, trees and
terrain heights. This moved up to right after P1.

GitHub Pages can't run a server, and calling map APIs live from players' phones would hit rate
limits and keys. So the map is **pre-baked into the repo** by `scripts/bake-map.ts`
(`NODE_USE_ENV_PROXY=1 node scripts/bake-map.ts` in the cloud; downloads are cached in `.cache/`):

1. **Route**: Orlando → Atlanta → Chattanooga → Nashville → St. Louis → Kansas City → Denver →
   Boulder → Lyons → Estes Park → Rocky Mountain National Park, from the public OSRM server
   (OpenStreetMap data). About 1,920 miles, resampled every 20 m.
2. **Corridor strip** about 3 km wide along the route, cut into 4 km chunks
   (`public/map/c/NNNN.json`, ~770 files):
   - Terrain heights from AWS Terrain Tiles (Terrarium, USGS 3DEP / SRTM), sampled on a grid that
     follows the road (dense near the road, sparse at the edges).
   - Land cover (forest, water, farms, towns) from the USGS National Land Cover Database 2021.
     The game scatters low-poly trees inside real forests and yards.
   - Buildings (footprints + height, estimated where OSM has none) and nearby roads from
     OpenStreetMap via OpenFreeMap vector tiles.
   - Lane counts along the route from OpenStreetMap (Overpass), with defaults by road class.
3. `public/map/route.json`: chunk index, city waypoints with distances, a light overview line.

At runtime the game fetches the chunks around the car from the same site (no third-party calls),
builds meshes, and drops chunks it has passed. Credits (OSM/ODbL, OpenFreeMap, AWS/USGS, NLCD) are
shown in the footer.

## Milestones

### P1: Three.js scene, endless road
- Add `three`; new `src/scene/` with renderer setup, camera, lights, resize handling.
- Low-poly SUV, a 3-lane highway that scrolls endlessly (recycled road segments), lane markings,
  a few traffic cars on simple lane logic, roadside trees by biome (start with Florida palms).
- Replace the 2D `road.ts` canvas; existing upgrades and HUD keep working.
- Tests: pure helpers (segment recycling, traffic spacing). Screenshot check that WebGL renders.

### P2: Sensor view
- Perception model in pure logic: given owned sensors, what range/arc/object types are visible.
- Renderer shows only perceived objects; everything else fades to outline; draw the range ring.
- First sensor upgrades (front camera, radar) replace the old upgrade list.

### P3: Autonomy levels and takeovers
- `autonomy.ts`: features with sensor requirements, derived L0 to L5.
- Takeover events generated by road situations, tap to resolve, offline driving stops at an
  unhandled takeover. Lane lines turn blue when autosteer is active.


### P3b: Tiredness and crashes
- Tiredness meter in pure logic (rises with drive time, night, traffic; drops with breaks) and
  crash chance from tiredness plus missed takeovers. Unit tested.
- Crash sequence: the SUV and a low-poly family (Dad, Mom, kids, dog) plus loose luggage become
  physics bodies for a few seconds. Use **cannon-es** (small, pure JS, no WebAssembly) only during
  crashes; the normal drive stays scripted. Exaggerated forces and low gravity for the cartoon
  tumble, slow-motion camera orbit, see-through roof so the family is visible.
- The crash is deterministic from a seed so it can be replayed and screenshotted in tests.

### P4: Stream economy
- Viewers, $, gas tank, gas stations, stream gear upgrades, event pop-ups.
- New save version with migration from the current save format (old saves must still load).
- Offline summary screen.

### P1b: The real map (done early, owner request)
- `bake-map` script and committed map chunks; the car drives the real route over real terrain,
  past real buildings, forests and roads.

### P5: Route features
- Route strip / minimap, real landmarks and cities in the HUD, game distances tuned to the real
  1,920 miles, state gas prices, night/day cycle.

### P6: Polish and balance
- Tune costs and speeds to the 1-week trip target, tutorial hints, sound,
  arrival ending.

## Risks

- **Phone GPU performance.** Mitigated by low-poly, instancing, DPR cap; measure early in P1.
- **Route data licensing.** OpenStreetMap data is fine with attribution (ODbL); we avoid Google
  Maps data and any API that needs keys in client code.
- **Headless WebGL in CI/cloud.** SwiftShader is slow but fine for single screenshots; keep logic
  testable without WebGL.
- **Scope.** P1 to P3 already make a playable "car gets smarter" game; P4 to P6 can shift with
  feedback.
